1. Descripción General del Módulo

El módulo Notas de Gastos permite gestionar y registrar gastos operacionales de trabajadores. Está dividido en dos niveles:

Nivel 1: GastosOperarios

Interfaz simplificada donde los operarios pueden crear notas de gastos básicas (solo metadatos de la nota).

Nivel 2: NotasGastos

Interfaz completa para administradores y jefes de obra donde pueden ver todas las notas, añadir gastos detallados con tickets y OCR.

⚠️ Flujo recomendado:
1. Operario crea NotaGastos desde GastosOperarios (solo titulo, fechas)
2. Admin ve todas las notas en NotasGastos
3. Admin añade gastos individuales con tickets y OCR
4. Admin cierra la nota cuando está completa

3. Estructura de Componentes React

🎨 NotaGastosCard.jsx

Responsabilidad: Renderizar una nota de gastos expandible con todas sus operaciones.

Props recibidas: - nota: NotaGastos (objeto completo) - gastos: GastoOperario[] (gastos filtrados por nota_id) - operarios: Operario[] (lista de operarios) - canSeeAll: boolean (admin/jefe_obra) - myOperario: Operario | null (operario actual) - user: User (usuario logueado) Estados internos: - expanded: boolean (expandida/colapsada) - addGastoOpen: boolean (modal agregar gasto) - addAdelantoOpen: boolean (modal adelanto) - ticketPreview: string | null (URL de ticket en preview) - activeTab: 'gastos' | 'adelantos'

Mutaciones en NotaGastosCard:

  • createGastoM: Crea GastoOperario + actualiza total de NotaGastos
  • deleteGastoM: Elimina GastoOperario + ajusta total
  • cerrarNotaM: Cierra la nota (estado = 'cerrada')
  • reabrirNotaM: Reabre la nota (estado = 'abierta')
  • deleteNotaM: Elimina nota + todos sus gastos (cascada)

🎨 GastoDialogs.jsx

Contiene: Dos diálogos modales

AddGastoDialog:

Modal complejo con:

  • ✅ Upload de imagen/PDF
  • ✅ OCR automático con IA (InvokeLLM)
  • ✅ Campos: categoría, importe, fecha, proveedor, descripción
  • ✅ Validación antes de guardar
OCR Flow: 1. Usuario sube imagen/PDF (handleOcrUpload) 2. Se carga a storage via Core.UploadFile 3. Se invoca LLM con file_urls 4. 6. Flujos de Datos y Procesos

📊 Flujo 1: Crear Nota (GastosOperarios)

1. Operario hace click en "Nueva Nota"
2. Dialog abre con form (operario, título, fechas, notas)
3. Operario rellena datos y hace click "Crear Nota"
4. Validación: operario_id + fecha_inicio requeridos
5. Mutation: NotaGastos.create({...newForm, total: 0})
6. Success: Dialog cierra, lista se recarga (queryKey invalidate)
7. Toast: "Nota de gastos creada"

📊 Flujo 2: Añadir Gasto con OCR (NotasGastos)

1. Admin abre una NotaGastos expandida
2. Click en "Añadir gasto" → AddGastoDialog abre
3. Admin sube imagen/PDF
4. Upload: Core.UploadFile({file}) → {file_url}
5. OCR: Core.InvokeLLM({prompt, file_urls}) → {importe, proveedor, fecha, descripcion, categoria}
6. Campos del formulario se rellenan automáticamente (pre-populated)
7. Admin puede editar/validar datos
8. Click "Guardar"
9. Mutation: GastoOperario.create({...formData}) + NotaGastos.update(nota_id, {total: newTotal})
10. Cache invalidate: queries de gastos + notas se refrescan

📊 Flujo 3: Cerrar Nota

1. Admin click en "Cerrar nota"
2. Confirmación dialog muestra totales
3. Mutation: NotaGastos.update(nota_id, {estado: 'cerrada', fecha_cierre: today})
4. Nota cambia a estado cerrado (visualmente grisácea)
5. Botones de agregar gastos desaparecen
6. Aparece botón "Reabrir" (solo admin)

7. OCR y Procesamiento de Tickets

🤖 Pipeline OCR Completo

handleOcrUpload(file: File) { // Step 1: Upload file const { file_url } = await Core.UploadFile({ file }) // Step 2: OCR con LLM const res = await Core.InvokeLLM({ prompt: "Analiza ticket y extrae: importe, proveedor, fecha, descripcion, categoria (combustible|comida|material|...)", file_urls: [file_url], response_json_schema: { type: 'object', properties: { importe: { type: 'number' }, proveedor: { type: 'string' }, fecha: { type: 'string' }, // YYYY-MM-DD descripcion: { type: 'string' }, categoria: { type: 'string' } } } }) // Step 3: Mapear respuesta a form const extracted = res?.data || res || {} setForm(p => ({ ...p, ticket_url: file_url, importe: extracted.importe != null ? extracted.importe : p.importe, proveedor: extracted.proveedor || p.proveedor, date: extracted.fecha || p.date, descripcion: extracted.descripcion || p.descripcion, categoria: extracted.categoria && CATEGORIAS[extracted.categoria] ? extracted.categoria : p.categoria })) }

✅ Formatos Soportados

  • Imágenes: JPG, PNG, GIF, WEBP (OCR visual)
  • Documentos: PDF (OCR de texto extraído)
  • Texto extraído: Se envía como JSON a LLM para parsing

⚠️ Limitaciones

  • OCR depende de calidad de imagen (luz, ángulo, resolución)
  • PDF debe ser legible (no escaneado de baja calidad)
  • LLM puede no extraer correctamente si formato es no estándar
  • Usuario siempre puede editar datos extraídos manualmente

8. Problemas Identificados en Iteración Anterior

❌ Problema 1: Operarios no cargaban en dropdown

Causa: Línea 50 de GastosOperarios intentaba matching por email:
operarios.find(o => o.email === user?.email)
Pero los operarios creados manualmente NO tienen email de Base44 User.
Solución: Remover ese matching.
Los operarios y users son entidades desconectadas.

❌ Problema 2: No se veían notas creadas

Causa: RLS de NotaGastos bloqueaba la lectura por falta de creador validado.
Solución: Arreglar RLS para usar created_by con email del usuario autenticado.

❌ Problema 3: falta useEffect en imports

Causa: Componentes usaban useEffect pero no lo importaban de React.
Solución: Agregar import { useState, useEffect } from 'react'

❌ Problema 4: GastoOperario requiere nota_id mandatorio

Causa: Schema tiene "required": [..., "nota_id"]
Si no se pasa nota_id al crear gasto, falla la creación.
Verificación: NotaGastosCard siempre pasa nota_id en handleSaveGasto.
